F4: Checkout creation, resume, cancellation and worker reconciliation share an advisory lock. Immutable Stripe parameters and attempt time are persisted before submission. Recovery looks for an existing matching Stripe session before considering another submission, validates order identity/amount/currency, and refuses retries outside the safe window. Missing/expired parameters cannot create a perpetual blind retry. Reservation release requires sufficient evidence that no payable session remains. Concurrent payment updates are preserved. Dedicated admin adds authenticated, same-origin, rate-limited Stripe reconciliation with an audit trail; it does not create payments or refunds.
F5: Resend guards include original retryable failures, unknown delivery states and recently sent emails. Order locking prevents concurrent requests from enqueuing duplicates.
F6: Each worker lane catches transient errors and retries with bounded backoff. Heartbeats advance after successful work, errors remain visible, maintenance continues in email-only mode, and admin displays stale/erroring lanes and overdue email jobs.
F7: Confirmation polling retries transient HTTP/network/JSON failures with bounded backoff and request timeouts. Auth failures offer sign-in; exhausted retries offer account access and another check, with an explicit instruction not to pay again. Component cleanup cancels pending requests and timers. Analytics errors cannot invalidate payment confirmation.

Security conclusions and remaining hardening
No evidence of current key exposure was found in the inspected code, build outputs, live assets, reachable local history or sampled logs. It would be inaccurate to promise zero risk or certify all credential practices from these checks alone.
1. The three services share a standard sk_live Stripe key. Prefer separate restricted keys with only the operations each service needs; admin reconciliation needs read access. This limits the impact of a service compromise and enables independent revocation. No key was rotated during this audit. Stripe recommends restricted keys where possible: https://stripe.com/legal/api-key-security and https://docs.stripe.com/api/authentication .
2. Existing frontend production PostgreSQL TLS config sets rejectUnauthorized:false (also available under admin DB_SSL=true). Although these services use Railway private networking, this does not authenticate the database certificate. Configure a trusted CA and verified TLS where supported before claiming strict certificate-verification compliance. Changing this blindly could break database access, so it was not changed as part of ticket recovery.
3. Railway/Stripe account MFA, human access permissions, key age/rotation history, complete retained logs and API-key permission settings were not verified. Provider/error logging merits ongoing redaction protection; sampled logs contained no current secrets, but that cannot prove arbitrary future provider errors never contain sensitive data.
