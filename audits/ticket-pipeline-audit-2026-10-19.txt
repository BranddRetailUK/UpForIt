ORIGINAL FINDINGS (F1–F7 resolved 20 October; original evidence preserved below)

F1 — HIGH: Explicit email-provider rejections never retry automatically.
Evidence: frontend-next/scripts/email-worker.ts:166–177, 193–200; claimEmailJob at 58–72.
The worker commits sending_at before calling SendGrid. Every later error becomes unknown, including an explicit HTTP 429 rejection. The claimant only takes pending/failed jobs. A transient provider limit therefore stops delivery after one attempt, despite the five-attempt/backoff policy. This affects account verification/reset mail as well as ticket mail.
Reproduction: executed the actual failEmail function extracted from source against a rolled-back local PostgreSQL job with sending_at set and an explicit HTTP 429 response. Status became unknown and was ineligible for automatic claims.
Action: distinguish documented definitive rejection from ambiguous transport/acceptance failures. Retry retryable rejected submissions with backoff; surface nonretryable rejection as failed; reserve unknown for genuinely uncertain delivery. Preserve the protection against blindly resending an accepted message.
Provider reference: https://www.twilio.com/docs/sendgrid/api-reference/mail-send/mail-send

F2 — HIGH: Payment after event cancellation can still issue tickets and queue a normal confirmation.
Evidence: frontend-next/lib/ticket-payments.ts:23–24; frontend-next/lib/ticket-orders.ts:55–80; frontend-next/app/api/stripe/tickets-webhook/route.ts:65–77.
Paid-session correlation only holds an order when the scheduled sales deadline/event end is passed. It does not check a cancelled event or manually closed sales. If an existing Stripe session completes after cancellation but before expiry maintenance closes it, fulfilment issues valid rows with admissions_hold=false and the webhook queues the standard ticket email. The scanner correctly rejects a cancelled event, so the customer is charged and receives tickets that cannot admit them.
Reproduction: created a pending order, cancelled its event, then ran the actual correlated paid-session/fulfilment functions with the current event timestamp. Four tickets were issued with no admission hold.
Action: define the policy for in-flight payments after cancellation/manual closure and enforce it transactionally at fulfilment. Cancelled-event payments should enter review/refund handling and receive appropriate messaging rather than a normal admission confirmation. Keep date and closure history so late webhook delivery is not confused with a payment genuinely completed after closure.

F3 — MEDIUM: A terminal checkout reference blocks purchasing the same selection again.
Evidence: frontend-next/components/TicketSelector.tsx:61–71, 90–104; frontend-next/app/api/tickets/checkout/route.ts:38–46; frontend-next/components/PendingCheckout.tsx.
The browser saves checkoutKey per event and changes it only when the ticket selection changes. There is no clearing on payment completion, account cancellation, expiry or a terminal response. The API rejects that key for any non-pending order. A customer who pays or explicitly cancels and then selects the same quantity in the same browser tab is repeatedly told the checkout has finished. This also contradicts the cancellation message telling them they can start a new order.
Action: return a structured terminal state, link to the completed order, and rotate the key for an explicitly new purchase after the prior outcome is known. Keep the key stable during uncertain retries.

F4 — MEDIUM: An uncreated Stripe checkout can become permanently unrecoverable and block the whole account.
Evidence: frontend-next/app/api/tickets/checkout/route.ts:45–46, 54, 62–74; frontend-next/app/api/tickets/orders/[orderId]/checkout/route.ts:22–25; frontend-next/lib/ticket-maintenance.ts:5.
The committed payload includes a fixed expires_at. If no Stripe session was created, a later retry can violate Stripe's requirement that expiry be at least 30 minutes after creation. Near the cutoff the original expiry is only 31 minutes away, so a short outage can trigger this. The cancellation endpoint also tries to create the same invalid payload before expiring it. Pending orders without a session ID are excluded from maintenance, and any pending order blocks all new ticket orders for that user. After 23 hours the API explicitly requires admin reconciliation, but there is no dedicated admin recovery action for this state.
Action: distinguish definitive pre-creation failures from uncertain outcomes; reconcile by the persisted attempt identity before releasing stock; provide a safe, audited admin recovery path for missing-session orders. Do not simply discard reservations while a payable session might exist.
Stripe expiry requirement verified: https://docs.stripe.com/api/checkout/sessions/create (expires_at).

F5 — MEDIUM: A manual resend can coexist with a scheduled retry and send duplicate emails.
Evidence: frontend-next/lib/ticket-resend.ts:8–10; admin-service/data.mjs:52–54; frontend-next/scripts/email-worker.ts:58–72, 193–200.
The resend guard considers recent jobs and pending/processing jobs, but excludes retryable failed jobs older than two minutes. Those failed jobs remain claimable. After a PDF/configuration problem, pressing resend can enqueue a new job while the original remains scheduled; both may send when the underlying issue is repaired.
Reproduction: inserted an older failed job with attempts=1 and a future available_at, then called the actual resend function. Both the old failed job and a new pending job remained eligible for delivery.
Action: atomically reuse or supersede retryable failures when explicitly resending, or treat them as already queued. Keep unknown-delivery review separate.

F6 — MEDIUM: A worker lane can die while the process and other heartbeats remain alive.
Evidence: frontend-next/scripts/email-worker.ts:399–422; frontend-next/lib/ticket-maintenance.ts:5–7.
Exceptions from a lane's claim/heartbeat or from maintenance leave its infinite loop. Promise.all rejects; the top-level catch sets process.exitCode but does not stop the remaining loops/timers. The process need not exit, so Railway restart policy may not act. For example, an expiry configuration/database error can permanently stop maintenance while email heartbeats keep advancing. Supplying the missing Stripe key removes one trigger, not this failure mode.
Action: catch/retry bounded transient failures inside each lane, or terminate all lanes/process on unrecoverable failure. Track heartbeat/error state per lane and alert on stale queue age, not just a single email heartbeat. --email-only also omits periodic maintenance/recovery; production currently uses the full worker command.

F7 — MEDIUM: Confirmation polling stops permanently on a transient error or initially missing order.
Evidence: frontend-next/components/TicketConfirmation.tsx:34–36, 58–68; frontend-next/app/api/tickets/confirmation/route.ts:34–37.
Only a successful pending response schedules another poll. An initial 404 (e.g. Stripe succeeded but session persistence failed and its webhook has not repaired the association), a network error, or a temporary 5xx immediately sets a final error and stops polling. Buyers can see Order not found despite a successful charge, without the normal do-not-pay-again guidance.
Action: bound retries for transient/missing-yet statuses; show payment-confirmation uncertainty and account/retry actions. Treat auth expiry separately and do not infer payment failure from lookup failure.

Lower-priority follow-up
- The standalone frontend email-event handler has weaker batch validation than the dedicated ADMIN handler (frontend-next/lib/ticket-email-events.ts:13). Its permissive UUID regex permits invalid UUID strings and its timestamps are unbounded; malformed correlated entries can abort the whole transaction. The live ADMIN ingestion path has the stronger validation. Bring the alternate/Testing path into parity.
- Sequential ticket numbers remain an authenticated manual admission fallback. Train door staff to inspect the ticket/booking rather than accepting a verbally guessed number. This is not an unauthenticated QR-signature bypass.
- Scanning requires server connectivity. Use charged backup devices and a tested hotspot; do not maintain independent offline admission lists. Real phone-camera permission/lighting/printed-PDF testing remains required before the event.
